# Prop / device persistence across shots

A prop that appears in more than one shot must be the same object with the same
construction. Keeping the noun but changing how the object is built or operated is
a continuity failure even when both versions share a name.

## Name the exact construction, never the generic noun

- A generic noun is not a design. "Vehicle", "device", or "tool" does not say how the
  object is shaped, how it is operated, or how many parts it has.
- Always state the defining construction: silhouette and proportions, mechanism or
  control type, number and arrangement of parts, color, material, condition, and
  markings.
- When an approved prop asset exists, take every one of those details from its
  approved description or its Picture. Do not guess, modernize, or "upgrade" it.

## Bind the prop Picture in every shot that uses it

- Attach the same approved prop asset (same `asset_id` and `file_key`) to every shot
  where the object appears, and bind it as its own `<Picture N>`.
- The project continuity anchor pins each prop to its recorded asset and view. Do
  not swap in a similar but different prop.
- If the prop is displaced by the image-slot limit, keep it as explicit text
  guidance with the full approved design, and never let the model invent a different
  mechanism.

## Keep count and state consistent

- The number of instances, their color/condition, and what they carry stay constant
  across shots unless the story changes them.
- A prop change (damage, replacement, load change) is a deliberate, narrated change,
  not a silent redesign.

## When there is no approved prop reference

- Describe the object only as far as the approved metadata supports, and say what is
  not known rather than inventing a mechanism. Prefer creating an approved prop
  asset for any object that recurs.
